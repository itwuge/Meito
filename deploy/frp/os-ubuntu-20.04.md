# Ubuntu 20.04 已过标准支持期的处置

> 事实：系统镜像 `alibase_20231113`，Ubuntu 20.04 64 位。
> Ubuntu 20.04 LTS 的标准支持在 **2025-05-31** 结束；之后不再从常规渠道获得
> 内核、glibc、OpenSSL 等安全更新。继续长期在线必须二选一：
> **启用 ESM**，或**升级到更新的 LTS**。
> 具体支持截止日期以 Ubuntu 官方公告与本机 `pro status` 为准；本机状态**未验证**。

## 0. 先明确这台机器的事实

在动手之前，只做**只读检查**并记录：

```bash
cat /etc/os-release
uname -a
df -h /
free -m
# Ubuntu Pro / ESM 客户端是否存在、当前状态（只读，不 attach）
command -v pro || command -v ua || echo 'no pro/ua client'
sudo pro status 2>/dev/null || sudo ua status 2>/dev/null || true
# 当前 apt 源是否可用、是否有第三方源
grep -Rhs '^deb ' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null | sort -u
# 当前是否还有内核更新挂起
apt list --upgradable 2>/dev/null | head -n 20
```

需要记录但**不要猜**的项：

- Ubuntu Pro 是否已 attach、是否有可用的个人/企业订阅；
- 阿里云镜像是否自带 `pro`/`ua` 客户端并能访问 Ubuntu Pro 服务；
- 系统盘实际剩余空间；
- 是否有除 `alibase` 之外的第三方 APT 源；
- 安全组之外的宿主机防火墙规则（`ufw status`、`nft list ruleset`）；
- 当前内核版本与是否启用自动重启。

以上在本交付物中均标记「未验证」。

## 1. 路径 A：启用 ESM（推荐作为短期处置）

### 做法概要

1. 获取 Ubuntu Pro 订阅（个人可免费用于最多 5 台机器；企业需采购）。
2. 在维护窗口先做 ECS 快照。
3. 用 `pro attach`（或 `ua attach`）绑定订阅，启用 `esm-infra` 与 `esm-apps`。
4. 在维护窗口安装安全更新；内核更新后安排重启。
5. 用 `pro status` 确认 ESM 已启用，再跑一次 frps 验证清单。

> 本文档不直接把 `pro attach <token>` 当成生产命令发给你；订阅 token 本身也是凭据，
> 需要按凭据管理流程保管，并在快照完成后、维护窗口内执行。

### 优点

- 不需要跨大版本升级，变更面最小，回滚最简单。
- 继续获得内核、glibc、OpenSSL 等安全补丁，能覆盖当前最大的风险。
- 对 2 GiB / 40 GiB 的小节点更友好：不需要额外数 GB 的升级空间与两次重启。
- frp 是静态 Go 二进制，对发行版库依赖很低；ESM 足以让节点继续稳定服务。

### 缺点与限制

- ESM 只覆盖 Ubuntu 官方承诺的包范围；第三方软件、阿里云镜像自带组件、
  `universe` 中的部分软件不保证同等覆盖（`esm-apps` 的可用性需以订阅类型为准）。
- 发行版仍然是 20.04：后续工具链、文档、社区支持会持续退化，最终仍要升级。
- 引入 Ubuntu Pro 订阅凭据与外部服务依赖；节点需能访问 Pro 服务。
- 阿里云镜像是否预装/兼容 `pro` 客户端**未验证**；可能需要手工安装 `ubuntu-advantage-tools`。
- ESM 不改变「OpenSSH、systemd 等版本较旧」的事实；如果未来 frp 或运维工具要求更高版本，仍会受阻。

### 判据

- `pro status` 显示 `esm-infra` 为 enabled；
- `apt update` 不再提示 20.04 标准支持结束；
- 安装更新后 `uname -r` 与重启记录一致；
- frps 仍为 `active (running)`，验证清单的监听面与无回流检查全部通过。

## 2. 路径 B：升级到 22.04 / 24.04

### 升级路径

Ubuntu 官方支持逐级升级：**20.04 → 22.04 → 24.04**，不支持一步跳到 24.04。
因此要做两次升级、两次重启、两个回滚点。

> **本文档不提供 `do-release-upgrade` 的一行命令。**
> 生产机升级必须由操作者在快照完成、控制台可用、维护窗口内，按 Ubuntu 官方流程执行；
> 不允许在只有 SSH、没有带外控制台的情况下直接升级。

### 优点

- 回到受支持的 LTS：22.04 标准支持到 2027，24.04 到 2029（ESM 更长）。
- 获得更新的内核、OpenSSL、systemd 与云镜像支持，减少长期隐患。
- 以后安装/维护工具不会因为发行版过旧而被卡住。

### 缺点与风险

- 两次跨版本升级，每次都涉及内核、OpenSSH、netplan/cloud-init、GRUB、镜像源切换。
- 阿里云 ECS 的网络配置、cloud-init、内网 DNS 可能在升级后被重写；一旦 SSH 起不来，
  只能靠 VNC 控制台恢复。
- 40 GiB 盘、2 GiB 内存偏紧，升级过程需要额外空间与时间。
- 升级窗口内 frps 必须停止；节点不可用，所有新会话无法打洞协调。
- 若升级失败且无法在窗口内修复，只能回滚快照（整机回退，IP 不变，但会丢失窗口内变更）。

### 前置检查（每一项都要留记录）

| 检查项 | 判据/动作 | 不通过时 |
|---|---|---|
| ECS 快照 | 升级前创建实例/磁盘快照，记录快照 ID 与时间 | 不升级 |
| 配置备份 | 备份 `/etc/frp/`、systemd unit、journald drop-in、token 文件（root 只读） | 不升级 |
| 带外访问 | 阿里云控制台 VNC 可登录，且已验证 | 不升级 |
| 磁盘空间 | `df -h /` 至少有约 10 GiB 余量；建议 15 GiB（实际需求未验证） | 先清理或扩容 |
| 内存 | 2 GiB 可用；升级期间无重负载；确认没有 OOM 历史 | 先处理 |
| APT 状态 | `apt-get update` 正常、`dpkg --audit` 无残缺包、无 hold 的关键包 | 先修复 |
| 第三方源 | 暂时禁用非 Ubuntu/阿里云官方源，升级后再评估 | 不升级 |
| 网络配置 | 记录 `ip addr`、`ip route`、`/etc/netplan/*`、DNS；确认 cloud-init 行为 | 不升级 |
| 安全组 | 升级窗口内保持 7000 规则不变；不要同时改安全组 | 不升级 |
| 维护窗口 | 明确起止时间、通知使用者、准备回滚决策人 | 不升级 |

### 回滚点

1. **升级前快照**（最重要）：任何一步失败都可整机回滚。
2. **20.04 → 22.04 完成后**：先验证 SSH、网络、frps，再创建第二个快照，然后才继续。
3. **22.04 → 24.04 完成后**：同样先验证再收尾。
4. 每一步回滚后都要重新执行本目录的验证清单，不能只看 `systemctl active`。

### 判据

- 两项系统升级完成后，`/etc/os-release` 为目标版本；
- 能从公网 SSH（或 VNC）登录，网络/DNS 正常；
- frps unit 能启动，监听面与无回流验证全部通过；
- `pro status`（如果继续使用 Pro）状态正常；
- 记录升级前后内核版本、启动时间、frps 版本与验证结果。

## 3. 取舍建议

| 维度 | ESM | 升级到 22.04/24.04 |
|---|---|---|
| 变更风险 | 低 | 高（两次跨版本） |
| 工作量 | 小 | 大 |
| 维持时间 | 20.04 ESM 到约 2030 | 22.04/24.04 更长 |
| 磁盘/内存压力 | 小 | 大 |
| 长期技术债 | 仍在旧发行版 | 清除旧发行版 |
| 适合当前节点 | **短期到中期** | **中期到长期** |

建议顺序：

1. **如果 Ubuntu Pro 可用**：先在维护窗口启用 ESM，消除眼前的补丁缺口；
   同时把 22.04→24.04 升级排入计划，不要无限期停留在 ESM。
2. **如果 Pro 不可用或无法访问 Pro 服务**：优先安排升级，按 20.04→22.04→24.04
   两级推进，每级一个快照/回滚点。
3. 不要把「OS 升级」「frp 版本升级」「token 轮换」「安全组调整」放进同一个窗口；
   一次只改一类，出问题才能归因。

## 4. 与 frps 的关系

- frp v0.71.1 的 linux_amd64 发布包是静态 Go 二进制，不依赖目标机的 glibc 版本做动态链接；
  因此 20.04 ESM 或 22.04/24.04 都能运行。**这一点基于发布形式推断，尚未在真机验证。**
- 真正需要 OS 补丁的是内核网络栈、OpenSSL（若 frp 使用系统证书库）、OpenSSH（运维入口）等。
- 无论走哪条路径，升级后都必须重新执行 `verification.md`，尤其是：
  - `ss -lunp` 是否仍无 frps UDP 监听；
  - systemd 权限收敛指令是否被新版本 systemd 接受；
  - journald 容量上限是否生效；
  - 安全组规则没有被升级过程改动。
